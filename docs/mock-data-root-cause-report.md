# Root Cause & Data Origin Investigation Report

**Project:** StockFlow Enterprise — Inventory Management System  
**Investigation Date:** October 2026  
**Subject:** Persistence Analysis & Origin of Displayed Demo Products

---

## 1. Exact Root Cause

The products displayed at `http://localhost:5173/products` (e.g., Apple MacBook Pro 16", Logitech MX Master 3S, Samsung Galaxy Tab S9, Sony WH-1000XM5, Milwaukee Hammer Drill, Ergonomic Executive Chair, and two records of Vitest Industrial Sensor Pro) **are NOT hardcoded mocks in the frontend or backend**. 

Instead:
1. **Physical Persistence in PostgreSQL**: The 7 commercial demo products and their multi-warehouse stock balances, purchase orders, and sales orders were physically written into the PostgreSQL database during the initial system setup by `server/prisma/seed.ts`.
2. **Decoupled Seed vs Database State**: In the previous task, `server/prisma/seed.ts` was successfully rewritten to only bootstrap essential system metadata (Roles, Permissions, System Settings, Admin user) and forbid demo records on future seeding. However, because destructive deletion was explicitly prohibited without approval, the previously inserted rows remained in the PostgreSQL `Product` table.
3. **Real-Time Data Pipeline**: When the user opens the frontend, `ProductsPage` makes an authentic HTTP `GET /api/v1/products` call to Express, which queries PostgreSQL via Prisma (`prisma.product.findMany`). PostgreSQL truthfully returns the rows currently residing in its tables.
4. **Integration Test Artifacts**: The two "Vitest Industrial Sensor Pro" records were generated by automated integration tests running against the database without an `afterAll` teardown hook.

## 3. Duplicate Product Investigation ("Vitest Industrial Sensor Pro")

### Findings:
Two records exist in PostgreSQL:
1. `ID: 22489f9a-a154-429a-9105-59242c103d05` | `SKU: TEST-SKU-1791905171443` | Created: `2026-10-13T15:26:13.142Z`
2. `ID: f42e002c-1042-4ea9-ac3e-29f914f2cf09` | `SKU: TEST-SKU-1791908918981` | Created: `2026-10-13T16:28:39.412Z`

### Root Cause:
* In `server/tests/api.test.ts` (test case: `POST /api/v1/products should create a new product`), the test creates a product named `"Vitest Industrial Sensor Pro"` with a timestamped SKU (`TEST-SKU-${Date.now()}`).
* Because tests were executed twice against the development PostgreSQL database and lacked an `afterAll` cleanup hook, each test execution permanently persisted a test sensor record.

### Resolution:
* Added an `afterAll` hook in `server/tests/api.test.ts` that immediately deletes any created test product (`createdProductId`), preventing any future test run from leaving lingering records.

### Safety Guarantees of the Cleanup Script:
1. **Safety Dry-Run Gate**: Running without `--confirm` performs only a read-only preview.
2. **Transaction Isolation**: Wraps the entire deletion sequence in `prisma.$transaction`.
3. **Foreign Key Integrity**: Deletes child transaction records (payments, invoices, items, receipts, ledger entries) before parents to prevent constraint violations.
4. **Preserves Critical Infrastructure**: Never touches `Role`, `Permission`, `BusinessSettings`, or `User`.
